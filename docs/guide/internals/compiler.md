# Compiler pipeline

React Portal compiles components **on the instance**, in the platform's JavaScript engine, with no WebAssembly. The compiler (`src/server/compiler/compiler.ts`) is pure: no GlideRecord, so the same code could run in a browser or in Node. The build service (`src/server/build/build-service.ts`) wraps it with records.

```text
compilerInputs(owner)          main.tsx (client_script) + styles.css (css, if the kind has it) + extra client/style files
      │
      ▼
link()                         walk the import graph from main.tsx; Sucrase each reachable file once
      │                        (typescript + jsx + imports → CommonJS-style module)
      │                        resolve: ./relative → bundled · react, @portal/runtime, components:*, utilities:* → host
      ▼
emitModule()                   one ES module: a tiny module table + loader, host lookups via
      │                        globalThis.__REACT_PORTAL__.modules; exports default + __rpExports
      ▼
extractCandidates()            class-like tokens from every reachable code file
validCandidates()              keep the tokens Tailwind knows as utilities (design system, cached per script)
compileTailwind()              Tailwind v4 compile().build(valid) → moveVariantsToLayer()
      │
      ▼
index.js                       the module
index.css                      author CSS: styles.css, then imported .css files (unlayered)
utilities.css                  the component's own Tailwind sheet (the fallback, see below)
tailwind-candidates.json       the valid candidates, unioned per portal at reprocess
      │
      ▼
resolveRecordImports()         components:<ns>/<key> / utilities:<ns>/<key> → target builds (build_dep)
applyCompileResult()           assets, deps, server script, snapshots replaced together; reprocess
```

## Inputs per kind

`compilerInputs()` (`src/server/source/project-files.ts`) feeds the compiler only the baseline files the component's kind lists in `x_312987_portal.studio.kind_files`, plus any listed-elsewhere field that still holds legacy content. With the defaults, primitives compile `main.tsx` and `styles.css`, and utilities compile `main.tsx` only. Extra `client` and `style` files are fed for every kind. The same rule picks the server script (`serverScriptOf()`): a kind that doesn't list `server.js` and has an empty `script` field has nothing to run. See [Code editor](../studio/code-editor.md#virtual-files).

## Version

`COMPILER_VERSION = 'rp-server-compiler/6 (sucrase <v>, tailwindcss <v>)'`. It's part of every component build's **input hash**, so a compiler change (or a Sucrase/Tailwind upgrade) marks every build out of date; each recompiles on its next compile.

| Version | Change |
|---|---|
| 2 | Compiler version enters the input hash; Tailwind arbitrary values fixed |
| 3 | Blocks, record imports (`__rpExports`) |
| 4 | Class extraction splits only outside `[]` (`group-data-[collapsible=icon]:hidden`) |
| 5 | Variant layer (`rp-variants`) |
| 6 | Valid candidates only; `utilities.css` and `tailwind-candidates.json` split from `index.css`; `rp-portal` layer (one utilities sheet per portal) |

The vendor bundles in `src/server/compiler/vendor/` (`sucrase.js`, `tailwind.js`, with Tailwind's CSS sheets inlined, plus the host's `tw-animate-css` and `shadcn/tailwind.css` for the portal sheet) are generated by `npm run vendor:compiler` (esbuild, ES2019, neutral platform). `tailwind.js` also exports Tailwind's design system loader (`loadDesignSystem`). Regenerate after upgrading `sucrase`, `tailwindcss`, or the host's `tw-animate-css` / `shadcn`.

## Transform

Each file is transformed by extension: `.ts` → typescript + imports; `.tsx` → typescript + jsx + imports; `.jsx`, `.js`, `.mjs`, `.cjs` → jsx + imports; `.json` → `module.exports = <json>`. JSX uses the classic runtime (`React.createElement`); the emitted module injects `React` into every file. Sucrase errors carry `(line:col)`, turned into diagnostics.

## Linker

- Starts at `main.tsx`; queues every `require()` Sucrase emitted.
- Relative specifiers resolve against the importing file's directory: exact path, then `.tsx .ts .jsx .js .mjs .json .css`, then `<dir>/index.<ext>`. Escaping the project root is an error.
- `.css` imports become `{}` in JS and are appended to the CSS in import order.
- Host specifiers: `react`, `react-dom`, `react-dom/client`, `react/jsx-runtime`, `react/jsx-dev-runtime`, `@portal/runtime`, and any `components:` / `utilities:` specifier. A missing host module throws at evaluation (`React Portal host does not provide "…"`).
- Anything else: `Unknown import "…"`.

Dependencies are recorded as `relative`, `host` or `component` (record imports, matched by `^(components|utilities):[a-z][a-z0-9-]{0,39}/[a-z][a-z0-9-]{0,79}$`).

## Record imports

After a successful link, the build service resolves each record import to its component's build and fails the compile if the target doesn't exist, is the component itself, is the wrong kind for the prefix (`components:` → primitive/widget/block; `utilities:` → utility), or has no usable build. Widget imports whose `server_mode` isn't `none` add a **warning** that the default export renders as an embedded instance.

## Tailwind

The input stylesheet:

```css
@layer theme, base, components, utilities, rp-variants, rp-portal, rp-instance, rp-instance-variants;
@import "tailwindcss/theme" layer(theme);
@import "tailwindcss/utilities" layer(utilities);
@custom-variant dark (&:where(:host(.dark), :host(.dark) *, .dark, .dark *));
@theme inline { --color-<token>: var(--<token>); … --radius-sm…xl from --radius }
```

No preflight: the host's framework CSS provides it once. The colour tokens are the shadcn set plus `chart-1…5` and `sidebar-*`.

**Class extraction** is deliberately generous (Tailwind's own extractor is native code): split on whitespace and quotes, then on `{}<>=;\` outside square brackets, keep tokens of 2–160 characters that look like classes.

**Valid candidates.** `validCandidates()` keeps only the tokens that Tailwind's design system turns into CSS (`candidatesToCss`), checked against the portal input (a superset of the component input). The design system loads once per script, so a seed that compiles hundreds of components pays for it once. The output is byte-identical, but a portal union is about 20 times smaller: 2,157 valid classes instead of 65,009 raw tokens across all seed components. A raw union took 10–15 s to compile on the instance.

### Portal utilities sheet

Each component build's Tailwind sheet stands alone, and same-named layers merge across `<style>` sheets in the shadow root. So a later sheet's `px-2` beat an earlier sheet's `ps-4`, and a widget sheet's `flex-col` beat the host's `flex-row`. The variant layer fixed base against variant, but not base against base or variant against variant. The portal sheet fixes both:

- **Union.** At reprocess, `planUtilities()` (`src/server/release/portal-utilities.ts`) unions the `tailwind-candidates.json` of every build in the portal's manifest (layouts, placements, nested blocks and their transitive imports) with the host's classes (`HOST_CANDIDATES`), sorts the result and hashes it together with `COMPILER_VERSION`.
- **Reuse.** If the hash equals `release.utilities_hash`, the existing sheet is reused and nothing compiles.
- **Compile.** Otherwise `compilePortalUtilities()` runs once, at the end of the current script (Tailwind is asynchronous, and Promise callbacks run when the outermost script finishes). It writes `utilities_css`, `utilities_hash` and `utilities_meta` on the release, then reprocesses the portal again so the manifest points at the new sheet. Until then the manifest keeps the previous sheet, covering only the builds whose utilities didn't change.
- **Input.** The component input plus `@import "tw-animate-css"` and `@import "shadcn/tailwind.css"`, with utilities emitted straight into `@layer rp-portal`, the last layer. There's no variant pass: one sheet is already in Tailwind's order, and the layer puts every class in it above the same class in any other sheet. Polyfills are `@property` fallbacks only, which shadow roots need; the color-mix fallbacks are dropped (about 8% faster and 12% smaller).
- **Host classes.** `packages/portal-host/scripts/host-candidates.mjs` runs at the end of the host's `build:css` and writes `src/server/compiler/host-candidates.ts`. It scans the same sources as the Tailwind CLI, compiles every host class with the host's input and with the server's portal input, and **fails the build** listing any class whose CSS differs. The one accepted difference is the server's `dark` variant, which also matches `.dark` / `.dark *` (a superset). The file only reaches the instance with `now-sdk install`, so a host deploy that adds classes should be followed by an install, as releases already are. The framework CSS stays injected as before, so the host never depends on the portal sheet.
- **Serving.** The sheet is served at `/assets/<release id>/portal-utilities.css/raw?v=<hash>` to Studio users and to users who can access the portal. The bootstrap describes it as `utilities: { css, hash, covers }` (manifest v5), where `covers` lists the `utilitiesKey` of every build in the union.

Timings on dev189813 are in the [Styling](../authoring/styling.md#one-utilities-sheet-per-portal) page.

### Variant layer

`moveVariantsToLayer()` (`variant-layer.ts`, dependency-free string code) moves every variant rule out of `@layer utilities` into `@layer rp-variants`, except rules whose declarations are all `!important`. It runs on each component's own `utilities.css` (the fallback sheets), not on the portal sheet. Placement classes (`design/instance-style.ts`, `compileInstanceTailwind`) go through the same pass, then `renameLayers()` moves them to `rp-instance` / `rp-instance-variants`, above the portal sheet. It handles Tailwind's nested output and the CLI's flattened, minified output. The host's `build:css` runs the same code on the framework CSS (`packages/portal-host/scripts/variant-layer.mjs`), and placement classes get it through `compileTailwind`. See [Styling](../authoring/styling.md#cascade-layers).

## Output module

`index.js` is a self-contained ES module:

```js
// React Portal compiled component: app/x (rp-server-compiler/6 …)
const __rpm = globalThis.__REACT_PORTAL__.modules;
function __rpHost(id) { … }
const React = __rpHost('react');
const __rpDefs = { "main.tsx": function (module, exports, require, React) { … }, … };
const __rpMaps = { "main.tsx": { "./parts/Row": "parts/Row.tsx", "react": "@host:react", … } };
function __rpLoad(path) { … }
const __rpEntry = __rpLoad("main.tsx");
export const __rpExports = __rpEntry;
export default (__rpEntry && __rpEntry.__esModule ? __rpEntry.default : __rpEntry.default || __rpEntry);
```

## Server script

`compileServerScript()` stores the author's script unchanged, wrapped so errors surface:

```js
try {
<author script>
} catch (__rpCaught) { __rpError = { message: …, line: __rpCaught.lineNumber || null } }
```

The author's code starts on line 2; the executor subtracts 1 from reported lines. `SERVER_SCRIPT_FORMAT` (4) is part of the input hash, so a format change recompiles everything.

## Input hash and skipping

The snapshot hashed into `input_hash`: extra files (path, target, content hash), the server script, hashes of `client_script` and `css`, `tailwind`, exports, options schema and defaults, dependency spec, theme tokens and stylesheet hash, the runtime ABI property, the server-script format and the compiler version. When a ready build already has that hash and ABI, the compile is skipped (`upToDate`).

## Themes

Themes don't go through the compiler: `theme.css` is stored as written (`rp-server-compiler/1 (theme passthrough)`), and tokens travel in the manifest.

## Async on the instance

Tailwind's `compile()` is asynchronous, so compiles return Promises. In scoped scripts Promise callbacks run when the outermost script finishes; REST handlers may return a Promise (`http.ts` writes the body when it settles), and business rules and exec scripts finish their compile at the end of the transaction.

## Dry runs

`POST /rp_studio/components/{id}/check` runs `compileComponent` over the saved project merged with unsaved buffers and writes nothing.
